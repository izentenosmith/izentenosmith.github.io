Picture an internal platform where staff report operational problems at a large facility: a broken light, a blocked access road, a switch that stopped answering. Fixing one problem usually takes several teams. Electrical diagnoses, procurement orders a part, maintenance verifies the fix. Some steps must wait for others; some can run at the same time; every step has a deadline to acknowledge and a deadline to finish.

The hard requirement was that **none of this could be hard-coded**. Administrators needed to add new problem types, change which department handles a step, rewire the order of steps, and adjust deadlines, all from an admin panel and without a deploy. This post walks through the PostgreSQL model that made that possible, the parts I'm happy with, and the parts I'd change.

## Issues and tickets are different things

The first decision was to separate *what was reported* from *the work it causes*:

- An **issue** is one report: what happened, where, who reported it, who is affected, attachments and comments.
- A **ticket** is one unit of work needed to resolve that issue, owned by a single department and measured against its own deadlines.

One issue spawns many tickets. That split matters because people care about different things: the person who reported the problem wants to know when *their issue* is solved, while each department wants a queue of *its tickets*.

## Catalog, configuration, instance

Almost every table in the model falls into one of three layers, and keeping them apart is what makes the system configurable.

<CatalogToInstanceDiagram />

- **Catalogs** are plain lists of things that can exist: problems that can be reported (`issue_catalog`), tasks that can be done (`ticket_catalog`), departments, SLAs.
- **Configurations** combine catalog entries into something usable. An `issue_configuration` pairs a problem with its type; a `ticket_configuration` says *this task, done by this department, acknowledged within X minutes and finished within Y*.
- **Instances** are what happened at runtime: an `issue` points at the configuration it was created from, and each `ticket` points at the ticket configuration it instantiates.

Admins only ever touch the first two layers. Code only ever writes the third.

```sql
CREATE TABLE ticket_configuration (
  id                 int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  department_id      int NOT NULL REFERENCES department (id),
  ticket_catalog_id  int NOT NULL REFERENCES ticket_catalog (id),
  sla_response_id    int NOT NULL REFERENCES sla (id),
  sla_resolution_id  int NOT NULL REFERENCES sla (id),
  UNIQUE (department_id, ticket_catalog_id)
);

CREATE TABLE sla (
  id               int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name             varchar NOT NULL UNIQUE,
  time_in_minutes  int NOT NULL UNIQUE
);
```

Storing SLAs as plain minutes keeps deadline math trivial:

```sql
SELECT t.id,
       t.created_at + make_interval(mins => resp.time_in_minutes) AS respond_by,
       t.created_at + make_interval(mins => res.time_in_minutes)  AS resolve_by
FROM ticket t
JOIN ticket_configuration c ON c.id = t.ticket_configuration_id
JOIN sla resp ON resp.id = c.sla_response_id
JOIN sla res  ON res.id  = c.sla_resolution_id;
```

<Callout kind="note" title="A side effect of UNIQUE (time_in_minutes)">
  Because minutes are unique, two SLAs can never share a duration, so the table becomes a catalog of durations rather than of named agreements. "High priority, respond" and "Normal, resolve" can't both be 240 minutes. That turned out to be fine, but it's the kind of constraint worth deciding on purpose.
</Callout>

## One tree table for every taxonomy

Problems needed a *type* (incident, request, and subtypes under each) and tickets needed a *priority*. Rather than one table per taxonomy, both live in a single self-referencing tree:

```sql
CREATE TABLE hierarchy_node (
  id           int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name         varchar NOT NULL,
  description  varchar,
  "order"      int NOT NULL DEFAULT 0,
  parent_id    int REFERENCES hierarchy_node (id),
  UNIQUE (name, parent_id)
);
```

Each root is a taxonomy ("Issue type", "Priority") and its descendants are the values. Admins can add a new taxonomy level without a migration, and the admin UI is one generic tree editor.

The price is that foreign keys stop meaning much. `ticket.priority_id REFERENCES hierarchy_node (id)` happily accepts an *issue type* as a priority. The application enforced it, which works until someone writes a script. If I did it again I'd give each node a `kind` and use a composite foreign key so the database can check it:

```sql
ALTER TABLE hierarchy_node ADD COLUMN kind text NOT NULL;
ALTER TABLE hierarchy_node ADD UNIQUE (id, kind);

ALTER TABLE ticket
  ADD COLUMN priority_kind text NOT NULL DEFAULT 'priority'
    CHECK (priority_kind = 'priority'),
  ADD FOREIGN KEY (priority_id, priority_kind)
    REFERENCES hierarchy_node (id, kind);
```

Categories use a similar idea for filtering in the reporting UI: `category` is a flat list and `category_parents (child_id, parent_id)` links them, so one category can sit under several parents. Problems link to categories through a many-to-many table, which lets the same problem show up under "Electrical" and under "Lighting".

## The workflow is a graph, stored as a closure table

Here's the part that took the most thought. For each issue configuration, admins draw a graph of ticket configurations: which tasks start the flow, which wait for which, and which run in parallel.

<WorkflowDagDiagram />

Workflows are directed acyclic graphs, not trees: in the example, *Verify fix* has two parents. The obvious storage is an edge list (`parent_id, child_id`), but every interesting question then becomes a recursive query: *what has to finish before this step?*, *is adding this edge going to create a cycle?*

Instead, the model uses a **closure table**: it stores every ancestor–descendant pair along with the distance between them, not just the direct edges.

```sql
CREATE TABLE workflow (
  id                 int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  workflow_group_id  int NOT NULL REFERENCES workflow_group (id),
  ancestor_id        int NOT NULL REFERENCES ticket_configuration (id) ON DELETE CASCADE,
  descendant_id      int NOT NULL REFERENCES ticket_configuration (id) ON DELETE CASCADE,
  depth              int NOT NULL,
  UNIQUE (workflow_group_id, ancestor_id, descendant_id)
);
CREATE INDEX ON workflow (ancestor_id);
CREATE INDEX ON workflow (descendant_id);
```

For the example graph, the rows are:

| ancestor | descendant | depth |
| --- | --- | --- |
| Diagnose | Diagnose | 0 |
| Diagnose | Repair wiring | 1 |
| Diagnose | Order part | 1 |
| Diagnose | Verify fix | 2 |
| Repair wiring | Verify fix | 1 |
| Order part | Verify fix | 1 |
| *…plus a depth-0 row for every other node* | | |

`depth = 1` rows are the direct edges. Everything else is precomputed reachability. The self rows at depth 0 look redundant but make every insert a single statement.

### Adding a step

The admin panel offers two ways to add a node: **in series** (after an existing node) or **in parallel** (alongside one). Both are one `INSERT … SELECT`.

In series after node `:parent`: every ancestor of the parent, including the parent itself through its depth-0 row, becomes an ancestor of the new node, one step further away.

```sql
INSERT INTO workflow (workflow_group_id, ancestor_id, descendant_id, depth)
SELECT :group, ancestor_id, :new, depth + 1
FROM workflow
WHERE workflow_group_id = :group AND descendant_id = :parent
UNION ALL
SELECT :group, :new, :new, 0;
```

In parallel with node `:sibling`: the new node gets the same direct parents as the sibling. Grouping keeps the shortest distance when two parents share an ancestor.

```sql
WITH parents AS (
  SELECT ancestor_id AS id
  FROM workflow
  WHERE workflow_group_id = :group AND descendant_id = :sibling AND depth = 1
)
INSERT INTO workflow (workflow_group_id, ancestor_id, descendant_id, depth)
SELECT :group, w.ancestor_id, :new, min(w.depth) + 1
FROM workflow w
JOIN parents p ON w.descendant_id = p.id
WHERE w.workflow_group_id = :group
GROUP BY w.ancestor_id
UNION ALL
SELECT :group, :new, :new, 0;
```

### Connecting two existing steps

To make `:target` wait for `:source`, connect every ancestor of the source to every descendant of the target. First, the cycle check, which with a closure table is a single indexed lookup:

```sql
-- If the target already reaches the source, the new edge would close a loop.
SELECT EXISTS (
  SELECT 1 FROM workflow
  WHERE workflow_group_id = :group
    AND ancestor_id = :target AND descendant_id = :source
);
```

Then the insert, keeping the shortest distance for pairs that already exist:

```sql
INSERT INTO workflow (workflow_group_id, ancestor_id, descendant_id, depth)
SELECT :group, a.ancestor_id, d.descendant_id, min(a.depth + d.depth + 1)
FROM workflow a
JOIN workflow d ON d.workflow_group_id = a.workflow_group_id
WHERE a.workflow_group_id = :group
  AND a.descendant_id = :source
  AND d.ancestor_id = :target
GROUP BY a.ancestor_id, d.descendant_id
ON CONFLICT (workflow_group_id, ancestor_id, descendant_id)
DO UPDATE SET depth = least(workflow.depth, excluded.depth);
```

<Callout kind="tip" title="Why keep the shortest depth?">
  In a DAG the same pair can be connected by paths of different lengths. If you keep the shortest one, a row with `depth = 1` exists exactly when there is a direct edge, so "direct parents" stays a cheap, correct query.
</Callout>

### Running it

At runtime the graph answers two questions. Which tasks start a new issue? The nodes with no ancestors other than themselves:

```sql
SELECT n.descendant_id
FROM workflow n
WHERE n.workflow_group_id = :group AND n.depth = 0
  AND NOT EXISTS (
    SELECT 1 FROM workflow p
    WHERE p.workflow_group_id = :group
      AND p.descendant_id = n.descendant_id
      AND p.depth > 0
  );
```

And when a ticket closes, which tasks just became unblocked? Its direct children whose direct parents are *all* closed for this issue:

```sql
SELECT child.descendant_id
FROM workflow child
WHERE child.workflow_group_id = :group
  AND child.ancestor_id = :closed_step
  AND child.depth = 1
  AND NOT EXISTS (
    SELECT 1
    FROM workflow parent
    WHERE parent.workflow_group_id = :group
      AND parent.descendant_id = child.descendant_id
      AND parent.depth = 1
      AND NOT EXISTS (
        SELECT 1
        FROM ticket t
        JOIN current_ticket_state s ON s.ticket_id = t.id
        WHERE t.issue_id = :issue
          AND t.ticket_configuration_id = parent.ancestor_id
          AND s.state = 'closed'
      )
  );
```

<Callout kind="warning" title="A node is a ticket configuration">
  Using `ticket_configuration.id` as the node identity keeps the schema small, but it means the same task can't appear twice in one flow (say, "inspect" before *and* after a repair). If you need that, give workflow nodes their own id that points at a ticket configuration.
</Callout>

## Versioning by creating, not editing

Closure tables are pleasant to grow and painful to shrink: removing an edge means working out which indirect pairs were only reachable through it. The model sidesteps that. Workflows live in a `workflow_group` tied to an issue configuration, and **changing a flow means building a new group**. The newest group is the active one; older groups stay untouched.

That also gives you history for free. The weak spot is that "newest wins" is resolved by ordering on `created_at` in application code, so an issue opened yesterday will follow today's flow if it is re-evaluated. Two improvements I'd make:

- Store the `workflow_group_id` on the issue when it's created, so every issue finishes under the rules it started with.
- Make "active" explicit and let the database guarantee there's only one:

```sql
ALTER TABLE workflow_group ADD COLUMN is_active boolean NOT NULL DEFAULT false;
CREATE UNIQUE INDEX one_active_group
  ON workflow_group (issue_configuration_id) WHERE is_active;
```

## State as an append-only log

Tickets don't have a `state` column. Every transition is a row in `ticket_state_history` with the new state, who made the change and when. The current state is the latest row:

```sql
CREATE INDEX ON ticket_state_history (ticket_id, id);

CREATE VIEW current_ticket_state AS
SELECT DISTINCT ON (h.ticket_id)
       h.ticket_id, s.name AS state, h.user_id, h.created_at
FROM ticket_state_history h
JOIN ticket_state s ON s.id = h.state_id
ORDER BY h.ticket_id, h.id DESC;
```

The composite index lets PostgreSQL walk each ticket's history backwards and stop at the first row. Because nothing is overwritten, reporting questions come cheap. Time spent in each state is one window function:

```sql
SELECT ticket_id, state_id,
       lead(created_at, 1, now()) OVER (PARTITION BY ticket_id ORDER BY id)
         - created_at AS time_in_state
FROM ticket_state_history;
```

Comments work the same way: an append-only log per ticket, with optional attachment metadata, mixing human messages and automatic entries. Assignees are a plain many-to-many (`ticket_responsible`), so a ticket can have several people on it.

## The smaller decisions

A few other choices that held up well:

- **Roles are per department.** A `position (user_id, role_id, department_id)` table with a unique triple lets someone be a resolver in one department and a supervisor in another.
- **Author and beneficiary are separate.** Staff often report problems on someone else's behalf, so an issue records both, plus optional contact fields for an external requester who has no account.
- **Location is layered.** Zones, streets and landmarks are catalogs (streets map to zones many-to-many; landmarks belong to a zone). An issue stores coordinates plus optional references, including *two* street references, which is how you describe an intersection without inventing a table for corners.
- **Notifications are generic.** Each row carries `resource`, `action`, `resource_id` and an in-app `path`, so one table and one renderer handle every kind of event, in the app and by email.

## What I'd change

Most of what I'd revisit is the same theme: **rules the application enforced that the database could have.**

- Typed hierarchy nodes with composite foreign keys, as shown above.
- An explicit, uniquely indexed active workflow group, pinned on each issue.
- The "a category is either a parent or a child, never both" rule lives in the API; a trigger would make it impossible to break.
- Coordinates were stored as text. Today I'd use `numeric` columns or a PostGIS `geography(Point)`, which also opens the door to "issues within 200 m of here" queries.

The core ideas I'd keep without hesitation: separate catalogs from configurations from instances, store state as history instead of a column, and when the domain is a graph that admins edit, give the graph a closure table and let SQL answer the questions.
